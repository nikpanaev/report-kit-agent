# Первоначальная настройка

Цель: сотрудник выбирает рабочую область и самостоятельно входит в нужные сервисы; нет копирования чужих клиентов, чатов или авторизации.

Пользовательский порядок и опрос — [onboarding](onboarding.md). Следующие пункты выполняет агент; не выдавай их сотруднику как технический чек-лист. Доступ разработчика не переносится: actual host permissions, capability discovery, право записи в выбранную рабочую папку и доступ к сервисам проверяются отдельно. При read-only/отказе сохрани прогресс, выполни независимые разрешённые шаги и объясни одно нужное действие человека. Существующие ответы/разрешения не спрашивай заново; новые полномочия не выводи из наличия файла.

1. Прочитай package VERSION, dependencies.json и CHANGE-SPEC scope. Уточни ОС/Codex surface только если неизвестны. Поддержка устройства определяется фактической проверкой, не именем ОС в инструкции.
2. Сотрудник получает только ссылку report-kit-agent. Не проси искать второй репозиторий, выбирать версии или вводить команды. Прочитай поставляемый approved source и dependencies.json; проверь установленные bytes и фактическую доступность нужных скиллов. При их отсутствии/несовпадении выполни единый порядок [updates](updates.md#единый-порядок-получения-комплекта). Для локальной разработки допустим выбранный sibling package; это не способ установки сотрудником. Null URL означает неопубликованную сборку: не угадывай адрес. На настоящем опубликованном выпуске source настраивает сопровождающий заранее. Скачивание без исполнения; check_package для архива не требует Git. История с --history нужна только сопровождающему до выпуска. Первая установка требует прямого согласия; будущие совместимые обновления — по выбранному один раз режиму. Чужие namespaces/source не заменять.
3. Предложи отдельную private workspace вне обоих репозиториев; работодатель/владелец должен разрешить хранение нужных данных. Не ставить local workspace или credentials внутрь package/plugin cache. Уточни владельца приёмки и разрешённые способы sharing. Создать папку/локальные settings только по явно выбранному пути; plaintext secrets не записывать.
4. Workspace settings schema2 хранит пути, timezone, package identities report-kit-agent/report-kit-skills и доступные capability statuses, не passwords/cookies/API tokens. Пример assets/workspace.example.json синтетический и не является готовой конфигурацией. Старые settings не переписывать: отдельная проверенная настройка/миграция требует своего scope и сохранения данных. Клиентов пока нет. Profile/chat binding появляется только при отдельном подключении.
5. Показать фактические отсутствующие подключения. Google needed при первом документе, LiveDune при первых метриках, соцсеть/DM только при соответствующей съёмке; Gmail только для согласованного почтового источника. Не выдавать широкие scopes заранее. Выбор account для каждого new file сохраняется; setup не отменяет это правило.
6. Ключ LiveDune принадлежит сотруднику/разрешённому рабочему аккаунту; никогда не вставлять его в чат, argv или package config. macOS использует прежний Keychain. Для Windows подготовлен Credential Manager/ACL adapter; настоящую проверку выполняет пользователь по [короткому порядку](../docs/WINDOWS-CHECK.md), агент читает references/WINDOWS.md выбранного скилла LiveDune. До результата — USER_CHECK_REQUIRED, не поддержка по одному имени ОС. Новые каталоги создавать приватными, существующие проверять без молчаливого изменения прав. Иные ОС API CLI не поддерживает. Разрешённое web чтение отдельно от исправности CLI. VK использует собственную ручную авторизацию или явно разрешённый local CDP; новая личная сессия не поставляется.
7. Для UI нужна единая проверенная очередь всех навыков на этом устройстве. Если уже есть другие UI skills/очередь, согласовать совместимость одного store до первого UI действия; не создавать конкурирующие активные очереди. Наличие пакета не доказывает вызов skill из модели.
8. Сохранить setup receipt: package identities, selected workspace (private only), capability discovery vs actual invocation, checks PASS/FAIL/NOT_RUN/NOT_APPLICABLE, actions, blockers и next state. Offline package PASS не означает Google permissions или действующую сессию.

Если настраиваемую часть можно отложить до запроса, отложи её. Не требуй всех аккаунтов или всех соцсетей сразу. Никакой отчёт не собирается только из поручения на настройку.

После настройки источника версий предложи выбор «Применять проверенные совместимые обновления автоматически или каждый раз спрашивать?» По умолчанию, до ответа, ask_each. При compatible сохраняй отдельный private update-policy.json: source hash, точный original human locator и отзыв по [updates](updates.md). Это не разрешение изменить policy приложения, расширить права, принять новые hooks или мигрировать данные. Native approval/restart остаются отдельными реально требуемыми шагами. Без actual permissions/install route не обещай unattended activation; расписание при закрытом чате только по отдельному выбору и фактически доступному native scheduler, без собственного daemon.

Штатную установку и обновление сверять по [официальному порядку пакетов](https://developers.openai.com/plugins/build/plugins), фактические ограничения — по [правилам разрешений](https://learn.chatgpt.com/docs/agent-approvals-security). Repo/личные настройки, корпоративные требования и инструменты имеют отдельные границы. Не редактировать config вручную и не выполнять blanket marketplace upgrade до проверки candidate: такой refresh способен менять configured plugin cache. Сначала read-only source discovery и полный compatibility; затем только выбранная проверенная identity разрешённым native route.

Служебные чаты и maintenance registry настраиваются по [отдельному контракту](maintenance.md): сначала direct human creation/messaging authority, затем actual bindings и оригинальные human/tool locators в private workspace. Предложить координатора и сопровождающих только выбранных скиллов. Caller клиентского чата получает только свой profile/scope, coordinator контролирует полный client inventory. Наличие native thread tools проверять на выбранном Codex surface; при отсутствии не обещать автоматическую поддержку. Внешнее обращение разработчику через GitHub — отдельное разрешение, не продолжение локального grant.

Для LiveDune использовать reviewed dependency inventory из выбранного report-kit-skills. Текущий frozen graph требует Node>=20 через обязательный @hono/node-server2.1.3; root backend Node>=18 недостаточно. Actual executable/version проверить до credentials/install, не связывать это требование с клиентом без LiveDune. Python transitive versions, esbuild scripts/native binary и Chromium validation проходят выбранный platform/runtime probe; package metadata не поддержка устройства и не право установки.

## Как завершить настройку без технических заданий сотруднику

До подключения скиллов выбери внешнюю workspace, сохрани ожидания exact pair, ответы и blockers. На чистом устройстве clients пуст, capabilities NOT_READY, current agent identity проверяется; затем тот же полный preflight с --bootstrap. Отсутствующий --current-skills указывает на ещё не существующую собственную копию, а не чужую папку для перезаписи. Если агент уже имеет клиентов, bootstrap проверяет всех: это не обход несовместимости. Проверенные stage folders отделены от private workspace и любых active packages.

Выполни доступный штатный install route только после проверок и согласия. Если такого инструмента нет, подготовь проверенный точный local source штатным способом, затем объясни наблюдаемые пункты интерфейса: «Откройте раздел плагинов, выберите подготовленный Report Kit и нажмите “Установить”. Это добавит инструменты для отчётов. После установки вернитесь сюда». Названия кнопок сверяй по текущему приложению. При необходимости попроси перезапуск. Сотрудник не ищет адрес навыкового репозитория и не выбирает версии. Не редактируй cache/config приложения вручную и не выдавай доступ ко всему компьютеру. Если native route не умеет exact pair или безопасный возврат, установка отложена; не заменять это копированием поверх чужих скиллов.

После native readback двух фактически загруженных identities и вызова нужного навыка сохрани setup receipt. До этого «скачано» и «установлено» — разные состояния. Аккаунты подключай позже, по задаче. При offline без скиллов сохрани шаг и попроси восстановить интернет; при проверенном installed комплекте продолжай на нём.
