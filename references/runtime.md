# Подготовленная среда Report Kit

При повторном использовании архивов, проверке обновления и до разрешённого пробного запуска или исполнения скилла сверять не только runtime_id, но и версии Python, Node и библиотек во всех подготовленных слоях с рецептом выбранного агента. Это выполняют manifest_recipe_match/recipe_match в scripts/runtime.py; упаковка использует ту же проверку. verify подтверждает только байты/состав, не заменяет эту сверку или разрешение на исполнение.

Сотрудник не устанавливает Python, библиотеки или Node.js вручную и не вводит команды. Агент получает проверенные компоненты из приложений к опубликованному выпуску и выполняет доступные действия после нужного согласия. Это не изменение системных программ. Сейчас пакеты только подготовлены; установка, публикация и настоящая Windows ещё не проверены.

## Состав и получение

Core v3 также содержит python/REPORT-KIT-NOTICES.zip; точный supplemental input закреплён notice_package в рецепте. prepare_runtime проверяет его перед включением; prepare_release отказывает core с отсутствующим/изменённым комплектом. Оба шага проверяют inventory.json внутри ZIP: каждый перечисленный текст должен присутствовать и совпадать по SHA256; повторяющиеся имена запрещены. Сверка рецепта перед запуском также отвергает прежний хеш комплекта уведомлений даже при совпадении версий среды. Программные binaries сохранены, но эта добавка сама по себе не разрешает внешнее распространение — см. [лицензии](../LICENSE-STATUS.md).

Source of truth — assets/runtime-recipe.json: exact CPython distribution, platform wheels, все transitive Python packages и optional Node. Файлы поставки собираются prepare_runtime.py из уже скачанных проверенных upstream files, без pip, lifecycle scripts и исполнения скачанного кода. Отдельные assets: core (Python + tzdata), capture (Playwright + pyee + greenlet + typing_extensions), images (Pillow), livedune-node (Node с его штатными файлами). Pillow native libraries и Playwright driver остаются внутри exact wheels. Профили macos-arm64 и windows-x64 выбираются по actual OS/CPU; другие устройства пока не поддержаны этим рецептом. Номер библиотеки не доказывает совместимость всей среды.

Нативный исполнитель читает original опубликованный agent release и парную delivery запись. Тот же updates.delivery_check и stage_runtime_candidate проверяют источник, tag/full commit, опубликованность и exact asset URL; runtime.stage проверяет size/hash. Для stage_runtime_candidate исполнитель выбирает нужную платформу из draft-runtime-delivery: runtime_record содержит только schema_version, runtime_id, platform и assets выбранной платформы. Полный документ поставки с published/packages/platforms сюда напрямую не передаётся: его связь с опубликованной парой проверяется отдельно по оригинальным release readbacks. У stage_runtime_candidate нет отдельной CLI-подкоманды: это Python-функция существующего updates.py, вызываемая проверенным координатором; runtime.stage повторно проверяет архив, manifests, inventory и платформу. Не брать main/latest, случайный URL или self-reported checksum как trusted source. Первичное получение не исполняет файлы. Установку/исполнение выполняет native executor только после согласия и actual host permission. В исходный Git бинарные файлы не попадают. Строгий UTF-8/no-private-data source package guard сохраняется; binary archive mode используется только после separate runtime asset checks.

## Если на устройстве нет Python

Сначала штатно обнаружить готовую среду приложения; использовать её только для разрешённого шага и после проверки нужных возможностей. Не менять её, не копировать developer paths и не полагаться на системный python из PATH.

Если Python отсутствует, агент нативными инструментами скачивает выбранный exact **core** asset, сверяет источник и SHA256 и использует scripts/bootstrap_runtime.sh (macOS) или bootstrap_runtime.ps1 (Windows) только после согласия. Сотрудник эти команды не вводит. Native helper требует уже существующую выбранную внешнюю parent folder, создаёт новый private каталог, сверяет архив и отказывает links/traversal/чужим слоям; не запускает Python и не меняет PATH/global config. Core содержит собственный runtime-receipt.json; его SHA256 дан отдельно в asset record. После разрешения исполнения агент разрешает запуск только известных executable paths, выполняет runtime.verify/probe подготовленным core Python и сохраняет original tool readback. Shell/PowerShell security policy и macOS protection не отключать. При запрете — сохранить этап и объяснить одно действие либо необходимость ИТ-службы. Windows helper/ACL должен пройти настоящую пользовательскую проверку.

Полный runtime.stage создаёт новый inert каталог из core и только нужных layers. Для рабочего запуска runtime.execution_plan даёт argv с exact interpreter/private site и проверенным package script; global/user site не используется. Native permissions, UI queue, account/source/budget scope остаются прежними. Runtime receipt hash хранится отдельно в private selection; сверять его перед проверкой всех files. Сам receipt не является доказательством своего доверенного происхождения.

## Браузер по необходимости

Сначала проверить выбранный Chrome на конкретном скилле, с отдельным profile, без доступа к повседневному профилю пользователя. Shared browser_zoom принимает REPORT_KIT_BROWSER_CHANNEL=chrome/chromium; unset сохраняет прежнее поведение. Stories имеет --channel; messages при --profile использует Chrome и не принимает --channel. Не менять scale/light-theme/video/queue rules. Одно наличие Chrome не означает успешную проверку capture.

Если требуемого Playwright Chromium нет, спросить: **«Для этой задачи нужен отдельный браузер. Разрешите подготовить его? Ваш обычный Chrome и его настройки не изменятся»**. После отдельного согласия агент запускает штатный playwright install chromium из проверенной capture-среды, с отдельным private browser cache, проверяет версию/запуск и снимок. Native executor задаёт PLAYWRIGHT_BROWSERS_PATH на выбранную внешнюю private папку одинаково при подготовке и последующих запусках. execution_plan/browser_plan сами не выбирают этот путь; без подтверждённой настройки исполнителя изоляцию cache не считать проверенной. До согласия browser_plan возвращает ASK_BROWSER_CONSENT и не запускает установку. Chrome update/enterprise restriction не обходить переключением браузера: при policy_denied сначала ИТ-служба. Браузеры сейчас в подготовку не установлены; native install остаётся отдельным этапом. Системные браузеры не обновлять через playwright install chrome.

## Продолжение настройки

onboarding.next_step вызывается агентом при первом обычном обращении к активному Report Kit, без специального пользовательского запроса «настрой». Начни с приветствия и проверки инструментов. Сохраняй этапы discovery → workspace → runtime → packages → support → ready в private setup-progress.json через onboarding.record. Записывать только настоящие наблюдения с original locator, PASS/FAIL/UNKNOWN и выбранные несекретные ответы. Скрипт проверяет структуру, не истинность инструмента/согласия. Только координатор пишет setup. При незавершённой работе продолжать первый непройденный этап; изменившийся runtime/tool/permission инвалидирует соответствующий этап. Services подключать через отдельные observations только когда понадобились, не заранее. Passwords/keys в ответы не включать.

Запись атомарна: сбой сохраняет прежнюю запись; ревизия и exclusive lock препятствуют перезаписи конкурентом. При аварии native executor проверяет recorded lock PID и снимает lock только после доказанного завершения владельца и exact lock hash через recover_lock; неизвестного/живого владельца не снимать. При повреждённом progress сохранить его для восстановления, не сбрасывать ответы молча.

onboardingSkill уже указывает на packaged setup. [Официальный порядок OpenAI](https://developers.openai.com/plugins/build/plugins#add-an-onboarding-skill) описывает запуск скилла, когда пользователь запускает настройку после установки, в новом или текущем разговоре. Для Report Kit это ещё не проверено в настоящем приложении; доказанного приветствия сразу при открытии ссылки или до любого действия пользователя нет. Не обещать такого автозапуска и не добавлять обходной hook. На выбранной версии Codex проверить fresh/existing conversation отдельно после разрешения установки.

## Обновление и возврат

Использовать общий coordinator/preflight всех зарегистрированных клиентов. runtime-selection.json хранит runtime_id/root/receipt_sha256. Новую среду готовить отдельно, runtime-candidate.json — proposal, не активация; client_preflight проверяет её по candidate recipe и полному required_skills всех клиентов. Active runs по прежнему блокируют preflight. Ни старые настройки, ни клиентские файлы не переписываются этим планом.

Native rollout сохраняет exact previous package pair **и previous runtime selection**, активирует между отчётами, проверяет исходную задачу и при неудаче возвращает их вместе. Не откатывать данные клиента. Не удалять старую среду до успешного replay и пока на её interpreter ссылается запасной collector. Для fallback при setup передать prepare_fallback(..., python=<verified selected interpreter>); запуск двойным нажатием использует его, не требует manual Python install. Новые host rights/permissions не покрываются согласием на совместимые обновления. Настоящая установка/update/rollback ещё не подтверждены.

LiveDune Node layer не равен настроенному backend: по существующему exact dependencies/livedune/recipe.json агент сам подготавливает frozen backend в private каталоге после разрешения. У сотрудника не просить npm/pnpm/команды. Ключ и API checks — после готовности среды. Это по-прежнему отдельная native capability check, не вывод из наличия Node.

## Выпуск

prepare_release --runtime-assets добавляет проверенные готовые файлы в тот же local draft и SHA256SUMS, без remote/publish/install. Поставляемый draft-runtime-delivery связан с exact pair; published=false. Перед публикацией проверить все license/NOTICE files CPython, wheels, Node/npm/driver/native libraries; собственная MIT этого не заменяет. При новой OS/CPU/runtime пересобрать exact inventory, проверить native libraries, подпись/доверие и восстановление. Windows проверяет сотрудник после отдельного разрешения выпуска. Independent QA/security/license decisions не подменять self-tests.

Первый тестовый профиль: Windows11+ x64 или macOS14+ arm64. Windows Server, Intel macOS и Windows ARM пока не объявлены поддержанными; агент проверяет actual OS/CPU до исполнения среды. Требования — [официальная документация Playwright](https://playwright.dev/python/docs/intro#system-requirements).

## Условия Windows-компонентов

Покажи [полный текст](windows-terms.md), затем задай отдельный вопрос о подготовке и принятии условий. Достаточно прямого ответа «да»; не требуй специальной фразы. Неоднозначный ответ уточни, отказ не заменяй согласием. Прямой ответ и штатное разрешение конкретного действия проверяет исполнитель. Эта инструкция не является доказанным окном согласия в приложении.

После подтверждения текущего текста штатным файловым инструментом создай private windows-terms-consents/<terms_sha256>.json вне пакетов. Имя — SHA256 всей страницы условий строчными буквами. Формат записи прежний: accepted=true, terms_sha256, response_locator. Locator указывает на исходный ответ; сообщение целиком, аккаунты, ключи и клиентские данные не копируются. Только координатор пишет настройку. Сохраняй новую запись в новой папке с правами выбранной private workspace; не меняй чужие файлы. Если подходящее действующее подтверждение уже есть, повторный вопрос и запись не нужны.

**Не заменяй старые подтверждения и windows-terms-consent.json.** runtime.windows_terms_record(workspace, digest) выбирает точный файл из windows-terms-consents; при его отсутствии читает прежний одиночный файл, если он существует. Затем windows_terms_check проверяет accepted, точный хеш и locator. Найденный повреждённый, отказной или иной неверный файл не заменяется старым положительным подтверждением. При отказе сохраняй этап; при отзыве согласия не используй прежний положительный ответ. Сохранённые подтверждения нужны для возврата и не удаляются при обычной очистке временных файлов.

Перед probe/execution_plan используй подходящую запись как terms_acceptance. Пока Python ещё недоступен, запись выбирает штатный файловый инструмент по тем же правилам, а bootstrap_runtime.ps1 получает TermsAcceptedSha256/TermsResponseLocator. Общая проверка обновления использует ту же историю. При новых условиях добавляется новая запись; прежняя пара, в том числе со старым читателем одиночного файла, сохраняет своё согласие. Locator выбранной записи сохраняется в существующем этапе runtime через onboarding.record после успешной проверки среды.

Windows bootstrap возвращает отдельные безопасные коды RUNTIME_WINDOWS_TERMS_CONSENT_REQUIRED, RUNTIME_PERMISSION_REQUIRED, RUNTIME_HASH_INVALID, RUNTIME_CHECKSUM_FAILED с понятным следующим шагом. Неизвестная причина получает только RUNTIME_BOOTSTRAP_FAILED; свободный текст исключения и личные пути не выводятся. Это подсказки для агента: сами по себе они не разрешают повторную установку, новое скачивание или обход запрета. Скрипт хранится в UTF-8 с BOM для чтения кириллицы Windows PowerShell 5.1 по [правилам Microsoft](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_character_encoding?view=powershell-5.1). Политики исполнения и защиты не меняются.

Текст и оригинальный Python LICENSE закреплены по хешу; stage остаётся инертной проверкой файлов без запуска. Подтверждения хранятся приватно и не включаются в архив поддержки. Произвольный JSON не доказывает человеческого согласия. Настоящие PowerShell, русские сообщения и первый запуск на Windows ещё требуют проверки сотрудником. Готовые бинарные слои v3 не изменены. [Лицензионные границы](../LICENSE-STATUS.md) и отдельное разрешение публикации сохраняются.
