# Передача сотруднику

## Что уже подготовлено

Два локальных package/plugin репозитория с отдельными VERSION и чистой исходной историей. Здесь общие инструкции и setup, в report-skills reusable source modules. Существующих клиентов/аккаунтов/чатов/готовых отчётов внутри нет.

## Предлагаемый полный план

План дополнен по запросам владельца от 14.10.2026 о регулярных выпусках, совместимости и обмене между клиентскими и сопровождающими чатами. Это план следующей работы, не действующая автоматизация, разрешение публикации или установки. Периодичность, новые адресаты, их полномочия и канал обновлений требуют принятия перед применением. VERSION и установленное поведение этим документным изменением не повышаются.

1. **Закрепить переносимый цикл сопровождения.** Отделить исполнение отчёта, сопровождение общего процесса и сопровождение конкретного скилла. В полном контракте сохранить обращение → воспроизведение → исправление → ответ → повтор исходного шага → закрытие. Переносимая версия сейчас содержит update/context refresh, но полного incident/callback/replay цикла в ней нет. Не считать подготовку пакетов равной переносу этой возможности.
2. **Добавить локальный реестр ролей и разрешений.** Хранить client/skill ID, точный thread/host/project binding, версии и ограниченное прямое полномочие человека только в private workspace. Настройка предлагает один чат сопровождения отчётов и отдельные чаты нужных скиллов; создаёт их только по явному поручению, остальные откладывает до необходимости. Привязки сотрудника проверяются заново; старые адреса, аккаунты, чаты и разрешения не импортируются. Название помогает выбору, но не заменяет binding и подтверждение роли. Комментарии VK направлять в vk-comment-screenshot, личные сообщения — в vk-message-screenshot. Неизвестный/недоступный адресат означает prepared/blocked, без отправки запасному чату.
3. **Стандартизировать служебное обращение.** Локальный incident ID, origin binding, версия/hash, ожидаемое/фактическое, минимальный воспроизводимый случай, разрешённые действия, остаток бюджета и обезличенный результат проверки. Общая ошибка процесса идёт координатору; ошибка capability — её сопровождающему. Дубли продолжать под одним ID, не пересылать по кругу; занятый чат не получает повторные поручения. Операционные сбои доступа/сети/данных сначала отличать от дефекта. Не передавать keys/cookies/sessions, всю переписку или клиентский corpus.
4. **Обеспечить проверяемое исправление и возврат.** Клиентский агент не редактирует общий код. Единственный назначенный редактор готовит минимальную правку в изолированной task branch, сохраняет failure и проверяет исходный случай/affected regression; общий Git и UI используют свои согласованные блокировки. Ответ содержит incident ID, точную исправленную identity, проверки, ограничения и шаг повтора. Статусы различают delivered, acknowledged, fixed candidate, awaiting origin verification, resolved и blocked. Closed только после успешного исходного replay в прежнем разрешённом scope/budget; failed replay сохраняет incident открытым. Callback/обновление не снимают паузу пользователя и не запускают новый отчёт. Нужные получателю файлы сохранять до подтверждения получения/использования и приёмки; явно различать proof-only receipt и доступный материал для отчёта. Удаление — затем по точному inventory.
5. **Подготовить выпуски двух репозиториев.** Каждая принятая общая правка рабочего процесса/скилла проходит reviewed portable import, сохранение provenance и affected checks. Автоматической связи с исходными рабочими версиями сейчас нет. Выпуск report-agent выбирает точный проверенный report-skills комплект; число скиллов может расти без подключения всех аккаунтов заранее. Предлагаемые каналы — экспериментальный и рабочий; публикация примерно раз в неделю при принятых изменениях, важные fixes вне очереди. Подготовка draft release автоматизирована, публикация только после разрешения. Public payload/history, лицензии, зависимости, tests, immutable artifact identity и changelog проверяются до выпуска. Общий release index хранить в report-agent; третий репозиторий не нужен.
6. **Добавить обнаружение обновлений и compatibility preflight.** Предлагаемый default — проверить утверждённый рабочий канал перед работой не чаще раза в сутки, без сообщений при отсутствии изменений; offline сохранить текущую версию. Фоновый опрос при закрытом приложении не обещать без отдельного механизма. Preflight использует локальный реестр всех клиентов: common/skill versions, profile revision/hash, template/source/workspace contracts, permissions и pauses. Проверять изменения требований и affected regression; номер версии/hash или ответ AI не доказывает совместимость. Неполный/устаревший реестр блокирует общий rollout. Если общий installed skill несовместим с одним клиентом, не заменять его глобально; совместное хранение разных версий сначала требует реальной host/isolation проверки.
7. **Проверить установку, refresh и откат.** Применять exact approved pair между заданиями через поддерживаемый native host route; учитывать кеш установленного плагина и подтвердить фактически загруженные identities. Сохранить предыдущий комплект и проверенную возможность отката. Собственные явно разрешённые клиентские чаты перечитывают новый common и только свой профиль, пишут receipt/history; координатор проверяет actual ACK, pauses и blockers. Missing ACK означает pending/partial, а не успех. При неудаче восстановить выбор совместимого комплекта без перезаписи отчётов, профилей, workspace, permissions, sessions и последующих owner edits. Миграция private schema требует отдельного dry run, backup, разрешения и проверенного восстановления; package rollback не считается data rollback.
8. **Проверить весь цикл на изолированных примерах.** Покрыть правильного/неправильного адресата, missing permission, дубли, busy/unavailable, callback без replay, failed replay, pause, потерю нужного файла и восстановление. Дополнительно совместимое/несовместимое обновление, частичный refresh, старый клиентский override, offline, нарушенную identity, отказ установки и rollback. Synthetic проверки не заменяют actual messaging/host install/service checks. Никаких реальных outages, новых расходов или клиентских изменений ради теста без отдельного scope.
9. **Провести перенос на устройство сотрудника.** После прав и проверки лицензий опубликовать разрешённые релизы; public URL сейчас отсутствует. Сотрудник получает одну ссылку, разрешает установку, выбирает private workspace и разрешённые служебные маршруты, подключает свои сервисы только при необходимости. Публикация в upstream/GitHub Issue и сообщения людям вне локальных маршрутов требуют отдельного разрешения на конкретный обезличенный payload; чаты разных аккаунтов не считать автоматически доступными. Затем новый клиент, согласованные правила, pilot, отдельная base-template acceptance и полный control report. В той же среде проверить обращение/исправление/origin replay, update/refresh/rollback/cleanup. Только это подтверждает перенос для выбранного устройства и аккаунта.

## Удобство сотрудника

Один выбор при настройке задаёт явно ограниченные служебные маршруты и callback для указанных локальных ролей; это полномочие сохраняется приватно и может быть отозвано. Оно не включает публикацию, новые логины/права, увеличение бюджета или продолжение paused отчёта. Для обычного исправления показывать только существенный итог и необходимое действие; если нужно участие человека, задать один конкретный вопрос. Для обновления — коротко что изменилось, какие клиенты проверены, что блокирует и можно ли применить; технические receipts остаются локально.

Отсутствие native messaging/install на выбранной поверхности показать как ограничение setup; не обещать равноценную автоматическую работу по одному чтению инструкций. До подтверждения скоупа и actual host tests текущая переносимая версия остаётся local preparation.

## Зависимости и единый исполнитель исправления

Матрица совместимости учитывает не только клиент → skill, но и skill → другие skills/общие helpers/runtime/provider contracts. Правка общего VK engine может затронуть посты и комментарии; исправление UI-очереди — несколько платформ. Сопровождающие роли согласуют одного редактора связанного изменения; сохраняются очередь Git и одна UI-очередь на устройстве, без конкурирующих установленной/переносимой копий. До rollout проверяются полные affected source/installed identities, не только SKILL.md; имя скилла и сообщение «исправлено» этого не доказывают. Одновременные callbacks не запускают несколько replay или установок одного incident. Namespace conflicts со сторонними/старым installed пакетом выявляются setup и не решаются молчаливой перезаписью.

## До публикации

- Выбрать distribution license, подтвердить права на исходники и dependency notices.
- Разобрать нестабильную синтетическую проверку VK rate limit: cold full run failed, isolated pass не отменяет failure. Не ослаблять pacing/no-retry/partial-source oracle.
- Independent QA/security, current plugin schema/host install, target-device/account/capability/permission checks, controlled update/rollback и cleanup drill.
- Задать real public URLs/exact release identities; повторно проверить весь Git payload/history на личные данные, secrets и raw artifacts. Не публиковать эту preparation автоматически.

## Обновление / поддержка

Сначала reviewed agent+skills pair, потом разрешённое обновление между заданиями. Client workspace сохраняется, no automatic migration. Exact old identity для отката; source snapshot не переписывать ради успешной проверки. При полномочиях на employee disconnect отзыв service grants/key и удаление его локальной сессии выполняются отдельно, не Git update.

Эти инструкции не обещают отсутствие технических настроек на ещё неизвестной ОС. Устройство, account permissions и живые сервисы остаются проверяемыми входами.
